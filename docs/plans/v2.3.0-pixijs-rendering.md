# v2.3.0 — Mascota con PixiJS (Rendering GPU)

**Status:** Draft (Gate 1 — PLAN)
**Date:** 2026-07-29

## 1. Goal

Migrar el rendering de la mascota de **SVG + CSS** a **PixiJS (WebGL 2D)** manteniendo el look 1:1, pero abriendo la puerta a:
- 60fps clavado en GPU (vs swap de `innerHTML` con micro-flicker)
- Bone hierarchy real (PIXI.Container anidados) → head turn, tail wag y leg movement con matemática de transformación, no CSS keyframes
- Tweening entre frames (cross-fade 120ms, no binary swap)
- Filtros y partículas built-in (motion blur, sleeping Z, mood hearts)
- 1 sprite sheet en vez de 18 archivos SVG sueltos

**No es un redesign visual.** Es un cambio de motor. Luna y Max deben verse idénticos al cerrar v2.3.0.

## 2. Scope

### In scope
- Reemplazar `petSvgWrapper` (en `src/renderer.js`) por un `<canvas>` con `PIXI.Application`
- Re-arquitectura de assets: cada parte del cuerpo (head, body, tail-base/mid/tip, leg-upper/lower) → un sprite separado, no un solo SVG
- Bone hierarchy: `PIXI.Container` anidados (body > head, body > tail, body > legs)
- Migrar `look-at-cursor` (rotación del container Head, no de un `<g class="pet-head">`)
- Migrar `tail wag` (tween de `TailBaseContainer.rotation`, no CSS keyframe)
- Cross-fade entre states (alpha tween 120ms, no swap directo)
- Partículas: sleeping Z + mood hearts, detrás de flag
- 1 motion blur filter (PIXI.BlurFilter) en tail tip, detrás de flag
- Tests: bone math, sprite loading, tween, particles

## 3. Architecture

### 3.1 Current state (lo que tenemos)

```
[renderer.js]
   petSvgWrapper.innerHTML = stateFrame  ← binary swap, micro-flicker
   <g class="pet-head" style="rotate(...)">  ← CSS transform
   <g class="leg" style="rotate(...)">        ← CSS transform
   tail wag: CSS @keyframes rotate
   rAF loop: animateTail()
```

### 3.2 Target state (PixiJS)

```
[renderer.js]
   PIXI.Application mounted on <canvas>
   Display tree (bone hierarchy):
     rootContainer (PIXI.Container)
       └─ bodySprite (PIXI.Sprite, texture: catBodySVG)
       └─ backLegUpperContainer (PIXI.Container) — pivots at hip
            └─ backLegLowerContainer (PIXI.Container) — pivots at knee
                 └─ backLegLowerSprite
       └─ frontLegUpperContainer
            └─ frontLegLowerContainer
                 └─ frontLegLowerSprite
       └─ headContainer (PIXI.Container) — pivots at neck
            └─ headSprite
                 └─ leftEyeContainer
                      └─ leftEyePupil
                 └─ rightEyeContainer
                      └─ rightEyePupil
                 └─ earLeftContainer
                 └─ earRightContainer
       └─ tailBaseContainer (PIXI.Container) — pivots at tail root
            └─ tailBaseSprite
            └─ tailMidContainer — pivots at end of tailBase
                 └─ tailMidSprite
                 └─ tailTipContainer — pivots at end of tailMid
                      └─ tailTipSprite (con BlurFilter)

   PIXI.Ticker @ 60fps:
     - updateHeadRotation()  // headContainer.rotation lerp toward cursor
     - updateTailWag()       // tailBaseContainer.rotation = sin(t * wagSpeed) * wagAmplitude
     - updateBreath()        // bodyContainer.scale.y lerp
     - updateStateMachine()  // cross-fade entre states
```

### 3.3 Asset strategy (la decisión clave)

**Decisión actual:** mantener SVGs, pero **dividir cada SVG en partes (head, body, tail, legs)**. Cada parte es una función que devuelve un SVG string. PIXI.Texture.from(svgString) en el momento de cargar.

**Por qué no sprite sheet PNG:** no tenemos asset pipeline. Construir uno (sharp, spritesmith, etc.) es scope creep. Los SVGs vectoriales se ven crisp en cualquier DPR.

**Por qué no procedural puro (Canvas 2D):** perdemos la calidad de ilustración de los SVGs. Reescribir Luna y Max en código es re-dibujarlas — eso es scope.

**Razón para el split por parte:** la bone hierarchy real requiere que cada parte sea un sprite independiente. Un solo SVG no se puede "rotar la cabeza sin rotar el cuerpo" en PixiJS sin slicing.

**Archivos resultantes:**
```
src/assets/
  cat.js     → catBodySVG, catHeadSVG, catTailBaseSVG, catTailMidSVG, catTailTipSVG,
               catFrontLegUpperSVG, catFrontLegLowerSVG, catBackLegUpperSVG, catBackLegLowerSVG
               (+ 4 walk frames para body y legs)
  dog.js     → mismo set para perro
```

### 3.4 Rendering resolution

- Logical: 256×256 (igual que ahora)
- `PIXI.Application` con `resolution: window.devicePixelRatio`, `autoDensity: true`
- En HiDPI (2x): canvas interno 512×512, CSS 256×256 → crisp en monitores retina

### 3.5 Speech bubble

**Se mantiene como HTML overlay** (no migramos a PIXI.Text — el text rendering en WebGL es un dolor). Se posiciona relativo al canvas con `getBoundingClientRect()`.

## 4. Implementation

### 4.1 M0: Spike (½ día) — **el gate de decisión**

**Objetivo:** probar PixiJS en Electron antes de comprometerse. Si M0 falla, pivoteamos a Canvas 2D o nos quedamos en SVG.

- [ ] `npm install pixi.js` (última estable, hoy v8)
- [ ] Crear `test/preview/pixi-spike.html`: PIXI.Application montada, 1 sprite dummy (rectángulo coloreado), rAF loop básico
- [ ] Levantar con `npm start` (o abrir el HTML directo) → verificar que el sprite aparece, FPS = 60
- [ ] Medir: memoria, CPU baseline, vs el SVG actual
- [ ] Decisión go/no-go: si FPS < 30 o hay errores en consola, replan

**Exit criteria:** pixijs se inicializa en electron renderer, sprite visible a 60fps, sin errores en consola.

### 4.2 M1: Pet window migration (1-2 días)

**Objetivo:** el pet window se ve igual que en v2.2.2, pero renderizado por PixiJS.

- [ ] Reemplazar `petSvgWrapper` en `renderer.js` con `<canvas>` + `PIXI.Application`
- [ ] Split de `cat.js` y `dog.js` en partes (head, body, tail, legs) — **sin redibujar, solo cortar** los SVG strings actuales por `<g>` boundary
- [ ] Cargar cada parte como `PIXI.Texture.from(svgString)`
- [ ] Construir el display tree de M1: solo `bodySprite` + `headContainer` + 4 leg containers (sin tail/eyes/breath por ahora)
- [ ] State machine: cycle de los walk frames existentes vía texture swap
- [ ] **Comparación visual lado a lado** con v2.2.2 — debe ser idéntico

**Exit criteria:** los 6 states (idle/walk/sleep/sit/lay/stretch) × 2 pets (Luna/Max) se ven idénticos al video de v2.2.2.

### 4.3 M2: Bone hierarchy (2 días)

**Objetivo:** migración real a bone hierarchy, no más CSS transforms.

- [ ] Implementar `src/core/pet-bones.js`: clase `PetSkeleton` con build del display tree
- [ ] `look-at-cursor`: en rAF, `headContainer.rotation = lerp(currentRotation, targetRotation, 0.15)`, target = `atan2(dy, -dx) * 180/π`, cap ±15°, threshold 250px (sigue idéntico al actual, pero ahora es Container rotation)
- [ ] `tail wag`: en rAF, `tailBaseContainer.rotation = sin(t * wagSpeed) * wagAmplitude` con lerp gradual de `wagSpeed` y `wagAmplitude` (mood-based, M4 de v2.1.0)
- [ ] Leg movement: `legUpperContainer.rotation` y `legLowerContainer.rotation` tweened en walk cycle (alternating front/back)
- [ ] Eliminar de `renderer.js`: CSS `transform-origin`, CSS keyframes de tail wag, el `<g class="pet-head">` lookup

**Exit criteria:**
- Head turn suave a cursor en 4 esquinas (no snap)
- Tail wag con `sin()` real, no `@keyframes`
- Mood change (calm → excited) produce lerp de wagSpeed gradual (v2.1.0 M4 sigue funcionando)

### 4.4 M3: State machine con cross-fade (1 día)

**Objetivo:** state transitions se ven fluidos, no hay snap.

- [ ] Implementar `src/core/pet-tween.js`: `tween(obj, prop, from, to, durationMs, easing)`
- [ ] En `setState()`: alpha tween 0→1 sobre el nuevo frame mientras alpha 1→0 sobre el viejo (cross-fade 120ms)
- [ ] Walk cycle interno: sigue siendo frame swap, pero con un alpha dip sutil de 50ms (anti-flicker)
- [ ] Mismo `STATE_FADE_MS = 120` que v2.1.0 (no romper el valor)

**Exit criteria:** transiciones idle→walk, walk→sit, sit→lay son suaves (verificable con video slow-mo).

### 4.5 M4: Effects (1 día)

**Objetivo:** los efectos que con SVG eran hacky ahora son triviales.

- [ ] `src/core/pet-particles.js`: `PIXI.ParticleContainer` con sprites de Z (sleeping) y ♥ (mood hearts)
- [ ] Sleeping Z: emerge del nose de la mascota cuando state=sleep, fade out, 3-5 partículas simultáneas
- [ ] Mood hearts: cuando `mood === 'excited'` o `mood === 'happy'`, spawnea un corazón cada 5-8s arriba de la cabeza
- [ ] `PIXI.BlurFilter` en `tailTipSprite`, strength 0.5 (apenas perceptible, da sensación de motion)
- [ ] Todos los efectos detrás de flags en config (default ON para Z, OFF para hearts en v2.3.0 — se prende en v2.3.1)

**Exit criteria:** 
- 3 efectos implementados, todos toggleables desde un objeto config
- FPS no baja de 55 con los 3 efectos activos simultáneamente

### 4.6 M5: Tests + docs (1 día)

- [ ] `test/pet-bones.test.js`: jerarquía de transforms (child position = parent position + own offset rotated by parent rotation)
- [ ] `test/pet-tween.test.js`: lerp a t=0, 0.5, 1; edge cases (NaN, Infinity, duration=0)
- [ ] `test/pet-particles.test.js`: spawn, update, despawn lifecycle
- [ ] `test/asset-split.test.js`: cada parte exportada tiene la misma viewBox/coord system que el SVG original
- [ ] Visual regression manual: comparar Luna/Max en v2.2.2 vs v2.3.0, confirmar idénticos
- [ ] Changelog v2.3.0 en `docs/deliverables/v2.3.0-changelog-2026-07-XX.md`
- [ ] `npm run sdlc:dev` verde
- [ ] Branch `feat/pixijs-rendering` lista para merge

**Exit criteria:** `npm test` pasa (940+ tests + nuevos), changelog escrito, sdlc:dev verde.

## 5. Risks

| Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|
| PixiJS v8 tiene breaking changes vs v7 | Medium | Medium | M0 spike valida la API actual antes de comprometerse |
| Asset split rompe algún path de carga existente | High | Medium | M1 mantiene `window.catXxxSVG` exports por compat, los nuevos PIXI textures se construyen al lado |
| Visual regression (Luna/Max se ven distinto) | High | High | M1 exit criteria = "idéntico a v2.2.2", comparación visual con screenshots |
| Bone math bugs (tearing, misalignment) | High | High | Unit tests rigurosos en M5, sanity check visual en cada M |
| PixiJS bundle bloat (~500KB gzipped) | Low | High | Aceptable en Electron (200MB+ ya). Medir post-M0. |
| Performance peor que SVG en hardware bajo | Medium | Low | Profile en M0. Si <30fps, pivotar a Canvas 2D |
| Speech bubble positioning rompe (HTML sobre canvas) | Low | Low | Mantener HTML overlay, posicionar con getBoundingClientRect |
| Eye tracking y blink animation se rompen al migrar | Medium | Medium | Pupila era un `<circle>` en SVG — en PixiJS es un `Graphics` o sprite. Migrar cuidadosamente. |
| AI (M3) no se entera del nuevo render y manda "walk" cuando no debería | Low | Low | Pet protocol (allow-lists) no cambia, solo el renderer. Si llega un intent válido, se traduce a state. |

## 11. Open questions

1. **PixiJS v8 vs v7** — v8 es la actual. ¿Hay alguna razón para usar v7? Mi voto: v8.
2. **Branch strategy** — propongo `feat/pixijs-rendering` nueva. La actual `feat/mascota-con-vida` (con v2.1 + v2.2) se mergea a main cuando vos digas. ¿OK o seguimos acumulando en la misma?
3. **Sprite sheet vs SVG parts** — empezar con `PIXI.Texture.from(svgString)` para velocidad. Si el performance de M1 muestra que cargar 18 SVGs por pet es caro, evaluamos PNG sprite sheet en v2.3.1. ¿OK?
4. **Eye tracking** — las pupilas hoy son `<circle>` con transform. En PixiJS serían sprites posicionados dentro del eye container. ¿Mantener el look actual (pupila moviéndose dentro del ojo) o rediseñar? Mi voto: mantener, es una firma de la mascota.
5. **¿Mostrar el plan a vos en formato visual (mock del árbol de display) o así está bien?** Si querés un wireframe, lo hago en M1 antes de tocar código.
